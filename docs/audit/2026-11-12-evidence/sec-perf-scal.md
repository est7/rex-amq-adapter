## SEC1 Trust derivation accepts an unrelated directory's symlinked .git file

- Severity: Medium
- Dimension: Security
- Evidence level: executed
- Evidence: `internal/trust/trust.go:184` and `internal/trust/trust.go:188` use `os.Stat` and `os.SameFile` on the registered `.git` file and the candidate's `.git` file. `Stat` follows symlinks, so a different directory containing a symlink to the registered file satisfies this check. `Derive` then adds that different directory to `trustedWorkspaces` at `internal/trust/trust.go:78`. Automatic callers are `internal/app/summon.go:353` and `cmd/rex-amq-adapter/main.go:567`; explicit `trust` calls the same derivation at `cmd/rex-amq-adapter/main.go:680`.
- Evidence: Run `REX_AMQ_ADAPTER_HOME=/tmp/rex-audit-20261112/probe-codex-01/state go run -mod=mod .` in `/tmp/rex-audit-20261112/probe-codex-01/`. The `trustProbe` function in `main.go` creates a real Git main checkout and registered orphan worktree, trusts only the main checkout in an isolated Antigravity settings fixture, and compares copied versus symlinked `.git` pointers. Output: `TRUST: copied pointer denied; symlink pointer settings_nonempty=true registered_in_git=false store_unchanged=true`.
- Impact: Calling `trust`, `tab`, or an Antigravity `summon` on an untrusted directory with this prepared link emits settings that trust the unrelated directory for that session. This violates the promise that only registered worktrees inherit existing repository trust. Preconditions are access to a real trusted checkout's registered `.git` pointer and a prepared candidate directory; this is not a remote exploit or a sandbox bypass between UNIX users. The actual Antigravity dialog was not exercised, but the incorrect settings passed to its launcher were verified.
- Fix sketch: Verify the candidate directory's identity against the directory containing Git's registered back-pointer, rather than equating only the `.git` files' target inodes. Keep directory symlink/case aliases to the *same directory* working. Add an unregistered-directory `.git` symlink regression beside `TestCopiedGitPointerDerivesNothing` (`internal/trust/trust_test.go:105`); also consider a hard-linked pointer, which has the same inode problem.
- Blast radius: `trust` output and the `--settings` argument of Antigravity launches through `summon`/`tab`. No persisted settings migration is required; the trust store should remain read-only.

## SCAL1 Summon can reserve a seventh worker from a stale session layout

- Severity: Medium
- Dimension: Scalability
- Evidence level: executed
- Evidence: `Summon` takes the layout snapshot at `internal/app/summon.go:82` through `FindSession`/`loadSession` (`internal/app/discovery.go:43`). Later, `reserve` refreshes records under the lifecycle lock but counts them with the *earlier* snapshot's `s.holds(rec)` at `internal/app/summon.go:231`; `s.holds` requires the record's block to be present in `windowOf` (`internal/app/discovery.go:72`). Adoption consumes the pending reservation at `internal/app/adopt.go:206` and publishes the live record at `internal/app/adopt.go:220` under that same lifecycle lock.
- Evidence: The same command as SEC1 runs `capProbe(false)` and `capProbe(true)`. A control with six visible live records reports `CAP: adoption_after_layout=false action=refused live_records=6 pending=0 launched=0`. The interleaving case starts with five records and a genuine pending `store.Summon`, returns the five-block layout, and completes the sixth record/reservation transfer under the real lifecycle lock before `reserve`. It reports `CAP: adoption_after_layout=true action=start live_records=6 pending=1 launched=1`. The fake terminal records a seventh launch request; no real agent is launched.
- Impact: Two overlapping summons near the cap can exceed the documented six-worker limit even though pending launches are counted and the lifecycle lock is held. Once the earlier launch adopts, it is in neither the later summoner's stale layout count nor its pending count. This is a specific concurrency window, not a claim that ordinary sequential summons fail or that the cap limits manually launched Rex agents. Existing `TestSummonPendingLaunchesCountTowardTheCap` (`internal/app/summon_test.go:251`) sequences the second summon before adoption and does not exercise this transfer between snapshot and reservation.
- Fix sketch: Count live records against a session layout refreshed within the lifecycle-locked reservation operation, so adoption cannot move a slot from pending into a live record invisible to that count. Alternatively count recorded placement conservatively until reconciliation. Add a barrier-controlled overlap regression using the layout/adoption/reservation order in the probe; no additional lifecycle state machine is needed.
- Blast radius: `summon` admission at the cap, including starts and resumes; pending-token and record formats can stay unchanged. Keep existing cycle, depth, stealth-agent, and live-delivery semantics.

## PERF1 Empty-inbox PostTool hooks rescan retained records and sent history

- Severity: Low
- Dimension: Performance
- Evidence level: executed
- Evidence: Every announcing hook calls `Store.Record` (`internal/app/hook.go:200`). Despite its single-record API, `Record` calls `readRecords` (`internal/store/store.go:165`), which opens and decodes every handle's JSON before selecting a block (`internal/store/store.go:235`). The same PostTool hook calls `checkableSent` (`internal/app/hook.go:227`); its `SentAfter` call (`internal/app/undelivered.go:50`) lists/sorts the entire outbox before filtering the already-checked cursor (`internal/amq/lifecycle.go:257` and `internal/amq/lifecycle.go:279`). Neither path depends only on new mail. The session watcher also enumerates retained inbox/outbox history to find the latest ID (`internal/app/narrator.go:48`).
- Evidence: Run `REX_AMQ_ADAPTER_HOME=/tmp/rex-audit-20261112/probe-codex-01/state go run -mod=mod . hook` in the probe directory. `hook.go` times the real `Env.Hook(EventPostTool, Codex, ...)` after fixture creation and one warm-up. Five interleaved rounds produced: six records/empty outbox median **0.164 ms**, range **0.115–0.169 ms**; 1000 records/empty outbox median **11.770 ms**, range **11.319–14.377 ms**; six records/20,000 already-checked sent files median **8.209 ms**, range **8.134–8.508 ms**. Every call returned no error and an empty notice. Records represent separate sessions, so the per-session cap does not bound this lookup. The old sent-file bodies intentionally are never parsed because every filename is behind the cursor.
- Evidence: A separate, untimed CPU-profile run (`go run -mod=mod . profile`, then `go tool pprof -top -cum -nodecount=25 hook.cpu`) attributed 400 ms cumulative sampled CPU to `Store.Record/readRecords` and 340 ms to `SentAfter/messageIDs` in a 40-round mixed workload. This maps the growing cost to filesystem reads/listings, rather than a failed or no-op hook. Host snapshot before measurement: 15 logical CPUs; load average 4.74/3.87/4.50, with other audit peers active.
- Impact: A quiet agent pays repeated filesystem work for unrelated sessions and previously processed messages on every tool call, and watchers pay repeated history enumeration while idle. The observed costs are small relative to the hook budget; this is retained-data scaling debt, **not** an established production timeout, regression against an earlier release, or estimate of live end-to-end agent latency. These warm-cache synthetic measurements exclude CLI startup and model/tool time; no capacity threshold is claimed.
- Fix sketch: Give block lookup a validated derived reference to its authoritative handle record, instead of decoding all records per hook. For sent history and latest-mail checks, reuse an unchanged-directory stamp/cursor or an incremental index so an unchanged outbox need not be enumerated each time; preserve behavior for new mail, deleted files, handle reuse, and raw AMQ sends. Measure realistic retained-state sizes before prioritizing a larger indexing change.
- Blast radius: Store lookup used by hooks/CLI identity, sent-cursor bookkeeping, and narrator/watch paths. Preserve current record ownership, incoming gateway checks, and JSON/CLI replies; any derived index must be rebuildable rather than a second authority.

## Strengths

- Doorbells ignore sender-controlled notification payloads and contain only fixed instructions, count, and a validated handle (`internal/app/inject.go:16`, `internal/core/inject.go:188`, `cmd/rex-amq-adapter/main.go:279`).
- Rex and AMQ subprocesses receive argument arrays, not shell-concatenated labels or message bodies; injector wrapper paths are shell-quoted (`internal/rex/rex.go:76`, `internal/amq/wake.go:315`, `internal/app/lifecycle.go:50`).
- Atomic state files start private (0600), directories are created with 0700, and lifecycle/ledger/inject locks serialize state writers (`internal/fsutil/fsutil.go:17`, `internal/fsutil/fsutil.go:49`).
- Incoming placed-agent mail fails closed on malformed headers; managed drain consumes only exact IDs admitted by its gate (`internal/app/gateway.go:89`, `internal/app/managed.go:181`).
- Injector history is trimmed and transcript tail reads are bounded, avoiding two common unbounded-log polling costs (`internal/store/store.go:273`, `internal/transcript/transcript.go:32`).

- Live process counts, six-real-agent concurrent startup, cold disks, many-session load, slow remote servers, and retention over weeks were not measured. The performance result supports only the synthetic hot-path claim above.
